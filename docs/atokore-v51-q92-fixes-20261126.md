## Phase 1　購入の取り消しが10分を過ぎてもできた（P1）

- **原因**
  - 10分の期限は、ボタンを**表示するとき**にしか確認していませんでした。
  - そのため、画面を開いたままにしたり、アプリがバックグラウンドで止まったりして表示が古いまま残ると、10分01秒でもボタンを押して取り消せていました。
  - 画面の下に出る取り消しバーも、同じ処理を確認なしで呼んでいました。
- **修正**（`polish-v44.js`）
  - 期限の判定を、取り消し処理の**最初**（何かを変える前）に移しました。バーとボタンのどちらから押しても必ずここを通ります。
  - 9分59秒までは取り消せます。10分00秒以降は取り消せません。取り消せないときは「10分を過ぎたため、取り消せません」と表示し、在庫数・見積もり・買い物リストは何も変えません。
  - 画面を開いたままでも、期限の瞬間に表示が消えます（あと何分かの表示は1分ごとに更新します）。
  - バックグラウンドから戻ったとき（`visibilitychange`／`pageshow`）にも、期限を確認し直します。
  - 二重タップと同時実行は、これまでどおり1回の処理にまとめます。処理中のボタンは「取り消し中…」と表示して押せなくなります。
- **期限の直前に始まった処理**
  - 期限は、ボタンを押して処理を始める時点で判定します。始まった処理は途中で止めずに最後まで実行します。サーバーの応答の後で止めると、在庫と見積もりがずれるためです。
- **端末の時計を変えた場合**
  - 経過時間は、壁時計（`Date.now`）と単調増加する時計（`performance.now`）のうち、長い方で数えます。
  - そのため、時計を戻しても期限は延びません。時計を進めた場合は、期限が早く来るだけです（安全側）。
- **家族共有のときの厳密な保証**
  - サーバー側の期限の草案を作りました（`supabase/proposals/atokore-purchase-undo-window-v51.sql`。適用はしていません）。購入がサーバーに届いた時刻から、サーバーの時計で10分です。
  - 期限の境目でアプリとサーバーの判定が分かれた場合は、サーバーの判定を優先し、何も変えずに期限切れと表示します。
- **E2Eテスト**（`stock-levels-v51.spec.cjs`。実際の画面で `page.clock` を使用）
  - 9:59 → 取り消せる。在庫・見積もり・買い物リストの行がすべて戻る。
  - 10:00 と 10:01 → 画面に残ったボタンを押しても拒否される。何も変わらない。
  - 画面に残った取り消しバーを10分過ぎに押す → 拒否される。もう一度押しても拒否される。
  - 開いたままの画面 → 10:00 でボタンが消える。
  - バックグラウンドから戻る → 期限を確認し直してボタンが消える。
  - 時計を5分戻す → 期限は延びない。
  - 二重タップ → 取り消しは1回だけ実行される。
  - 120→240→180 の既存テストも合格しています。
- **テストの効き目の確認**
  - 実行時の判定を外すと、10:00／10:01／バーのテストが失敗します。
  - 単調増加する時計を使わないようにすると、時計を戻すテストが失敗します。

## Phase 2　子どもごとの量が入っていると、合計を入れても黙って無視された（N-1b）

- **原因**：見積もりの計算は、子どもごとの量が2人分以上あると、入力された合計を使わずに子どもごとの合計で上書きしていました。
- **修正**
  - 「1日に使う量の入れ方」を選ぶ欄を追加しました。選択肢は「合計を直接入れる」と「子どもごとに入れる（自動で合計）」の2つです。
  - 選んだ方の数字を必ず使います。もう一方の値は消さずに残し、「子どもごとの量（4＋3）は消さずに残しています（今は使いません）」と表示します。
  - 計算に使う量を、入力中にその場で表示します（例：「計算に使う量：1日7枚（4＋3）」）。
  - 入れ方を変えて保存するときは、確認の画面を出します。保存した後も「変える前の設定に戻す」で元に戻せます。
  - 古いデータのうち、子どもごとの量が入っているものは「子どもごと」として開きます。どちらの入れ方か分からない呼び出しは、推測せずに拒否します。
  - 値の正規化は、保存するときだけ行います。対象は、表示上のずれ（5.599999904632568、2.5＋3.1）だけです。6、5.6、0.125など、入力した値はそのまま残します。
- **確認**
  - E2Eで次を確認しました：6・5.6・4＋3＝7の保存、再読み込みしても変わらないこと、両方向の切り替え、キャンセル、元に戻す、空の子どもごとの量は理由を表示して拒否すること。
  - ユニットテストでは、入れ方の判定と正規化を確認しました。
  - タップできる範囲の高さは44px以上です。ラジオボタンは、行全体（ラベル）が押せる範囲なので、ラベルの高さで測っています。

## Phase 3　写真の画面と省スペース表示

- **写真**
  - 通常の手順（ストック一覧 → 商品をタップ → 「写真を設定」）で開く「商品の写真」画面の中に、「写真枠の試用表示（合成データ）」を追加しました。
  - この画面の中で、無料5枚／有料20枚／有料プラン終了後を切り替えられます。そのまま、上限に達したとき・差し替え・終了後の超過の表示まで確かめられます。
  - 設定は、お試し画面の切り替えと同じもので、再読み込みしても残ります。
  - 写真のコードはlocalStorageに書き込みません（既存の安全テストのとおり、保存はbuild-infoが担当します）。
  - 写真ゲートはOFF、Supabaseなし、外部への通信は0件です（E2Eで確認）。
  - 試用の表示には、【試用表示・合成データ】と「※実際の家族共有・契約・サーバーの上限ではありません」を必ず付けます。
- **省スペース表示を正式な表示設定にしました**
  - 「写真付き3列／写真なし・詳細一覧」の切り替えのすぐ下に置きました。表示されるのは一覧表示のときだけです。
  - 初期値はOFFで、この端末に記憶します。「試作」という表記は外し、お試し画面からは削除しました。
  - 標準（OFF）では、すべての商品を1タップで変えられるままです。
  - ONにすると、余裕ありの商品だけを1行で表示します（変更は2タップ。設定欄にもそのことを書いています）。
  - 長い商品名は1行で省略します。全文は商品の詳細で確認できます。
  - 320pxではボタンを「余裕 ▾」と短くして、商品名を表示する幅を広げました。
  - タップできる範囲は44px以上で、横スクロールはありません。
  - 3列表示、横1列表示、ホームの2つのボタンは、そのまま残しています。

## Phase 4　写真のSQL（写真A／B）

`docs/atokore-v51-sql-approval-units-20261125.md` の「2026-11-26 追記」に詳しく書いています。

- **写真A**
  - 旧参照を新しい台帳へ移す処理を作りました（コピー → 照合 → CASでの確定 → 旧オブジェクトの削除 → 完了）。途中で失敗しても回復できます。
  - 孤児の回収は、冪等で、再実行でき、参照中の写真は消しません。
  - 解約した後、または権限を外された後には、確定を拒否します。
- **写真B**
  - 「旧オブジェクトは0件だが、旧参照が1件残っている」状態でも閉鎖できてしまう不具合を修正しました。閉鎖の条件は次のとおりです。
    - 旧参照が0件である。
    - 未完了の移行がない。
    - 台帳・参照・実体が一致している。
  - 同時に閉鎖しようとした場合の制御も入れ、実PostgreSQLで確認しました。
  - 既に配られたURL（CDN）の失効は、まだ合格ではありません。

## Phase 5　家族の担当・持ち物共有のSQLと、合成データでの試用

- **担当のSQL**
  - 返信がNULL・空白・不正な値のときは拒否します。
  - 家族から抜けた人の、担当と未送信の通知を整理します。
  - 送信の直前に、相手がまだ家族に所属しているかを確認します。
  - 使える世帯を、合成テスト用の世帯（サーバー側の許可リスト）に限りました。
- **持ち物のSQL**
  - 必須項目の欠落、空白だけの名前、不正なID、別の世帯の対象を拒否します。
  - 使える世帯を、合成テスト用の世帯に限りました。
- **合成データでの試用**（お試し画面「家族機能の試用（合成データ）」、`family-trial-v51.js`）
  - パパ／ママの画面を切り替えられます。
  - 担当のお願いと、「買えるよ」「今回は難しい」の返事ができます。
  - 2つの園に通う子ども2人について、明日の準備の担当を決められます。
  - 不足している物を買い物リストに追加できます。「買った」にすると不足が解消し、チェックを付けると「準備：完了」になります。
  - 家族が抜けた場合の動きも確かめられます。
  - 判定には、アプリの審査済みの規則（`family-prep-v51.js`）をそのまま使います。
  - 実際の家族共有・在庫・買い物リスト・サーバー・通知には一切触れません（E2Eで、実データが変わらないこと・外部への通信が0件であることを確認）。
  - 実環境の設定は、既定でOFFのままです。

- ロック画面に出す文には、商品名を入れません。
- 実際のプッシュ通知や有料のサービスは使っていません。

## Phase 7　安全な試用版のビルド

- `scripts/atokore/build-safe-trial.py` を作りました。内容は次のとおりです。
  - **接続設定**
    - 接続設定はnullにします。SupabaseのURLやキーは同梱しません。
    - 家族共有、クラウド写真、ログイン、OCRはいずれもOFFです。
  - **分離**
    - 保存領域、写真DB、Service Workerのキャッシュを、専用の名前（`atokoreSafeTrial`／`atokore-safe-trial-*`）に分けます。
  - **公開範囲**
    - ページにCSP（`connect-src 'self'`）と noindex を入れます。
    - 配信時のヘッダー（`_headers`・`vercel.json`）にも、X-Robots-Tag を入れます。
  - **記録と検査**
    - ビルドのSHAを表示し、全ファイルのSHA-256を `SAFE_TRIAL_MANIFEST.json` に書きます。
    - 接続設定、鍵のような文字列、古い保存名、OCRのON設定が残っていたら、ビルドを中止します。
- `scripts/atokore/check-safe-trial.cjs` でブラウザで確認しました（320／393／430px）。
  - 外部への通信が0件。
  - CSP違反が0件。
  - ページのエラーが0件。
  - 横スクロールが0。
  - 分離・SHAの表示・主な操作が正しく動く。
- 元の接続設定が入ったZIPは配りません。前回Work向けに作ったZIPは置き換えます。
