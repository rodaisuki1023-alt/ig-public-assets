# あとこれ：共有中の復元取り消しに関する確認（2026-11-05 JST）

## 結果と優先度

**P2：家族共有に参加する前の復元控えが残っていると、「復元する前の状態に戻す」から共有中の一覧を置き換えられる。**

公開元 `efc11f747e1a7fdafa927350361c3a029738f552` のコードで再現した。実世帯での発生事例を確認したものではない。通常の「バックアップから復元」は共有中に拒否するが、取り消し側の `undoRestore` / `undoRestoreConfirmed` には同じチェックがなかった。取り消しは在庫・買い物・いつものリストをまとめて保存するため、共有の監視処理が変更として送信する。

本PRは公開元に対する修正候補のみ。Pagesの公開元指定、main、SQL、実DB、実世帯、課金設定は変更しない。前日のレシート記録と家族除外の競合（PR #93）とは別の経路である。

## 再現・修正の根拠

`tests/e2e-v19/backup-undo-sharing.spec.cjs` に合成データだけの2ケースを追加した。

1. 共有開始前の控えを端末Aへ準備し、ローカルのAuth/RPCエミュレーターで世帯を作成、端末Bを招待する。Aで取り消しを選び、同期後のA/B双方の保存データを比較する。
2. 取り消しの確認画面を開いた後、共有状態を未参加から参加へ切り替える。こちらの状態遷移はスタブで分離して検証し、写真の取り消し処理の呼び出し数も確認する。

同じテストを公開元コードで実行すると2件とも失敗した。個人情報を含まない真偽値の観測は以下。

```json
{"scenario":"undo-while-sharing","localUnchanged":false,"partnerUnchanged":false}
{"scenario":"joined-during-confirmation","localUnchanged":false,"photoUndoCalls":1}
```

修正候補では共有可否の判定を通常復元と取り消しで共用し、取り消しの開始前と確認承諾後の両方でチェックする。共有中なら、一覧・写真・復元控えを変更する前に停止し、一覧が置き換わるため実行できない旨を表示する。

```json
{"scenario":"undo-while-sharing","localUnchanged":true,"partnerUnchanged":true}
{"scenario":"joined-during-confirmation","localUnchanged":true,"photoUndoCalls":0}
```

## 実行した検証と限界

- ローカルChromium：新規2ケースと既存の `storage.spec.cjs` / `w2-backup-share.spec.cjs`、計11件成功。保存容量エラー時の取消、読み取れない保存データの保護、旧試用版からのコピー、通常復元・取り消し、写真復元、共有中の通常復元拒否を含む。
- 保存起動処理の単体テスト：7件成功。
- 最終の案内文変更後、新規2ケースも再実行して2件成功（上の11件に含まれるケースの再確認であり、別の2ケースではない）。
- 2端末は独立ブラウザーコンテキストであり実機2台ではない。Auth/RPCはローカルのPGliteエミュレーター。今回の問題はブラウザーのガードと同期経路の確認で、PostgreSQLの並行ロック試験ではない。
- GitHub CIはPR作成後の結果を別途確認する。上のローカル結果をCI成功やSafari実機成功として扱わない。
- 本番アカウント・実世帯・実DBは使用していない。公開サイトの画面操作でこの破壊的経路を実行していない。

再実行例（依存導入済み、リポジトリ標準のPlaywright環境）：

```sh

node --test tests/atokore-storage-bootstrap-v19.test.cjs
```
