## 2. 利用者側で確認できた課題（公開レビュー・観察。推定市場規模ではない）

- [ママリの夫婦分担相談](https://qa.mamari.jp/question/25075142)：自分から気づいて準備する人とそうでない人の不均衡。単なる「共有リスト」が、家事分担の課題を解決しているとは限らない。
- [厚労省 トモイク資料](https://tomoiku.mhlw.go.jp/assets/pdf/kigyoubanryoushingakkyu_phase4.pdf)：家事・育児分担項目に、買い出し・ミルク・おむつ・保育園持ち物準備・送迎が含まれる。分担の見える化は公式の課題フレームと一致。

### S1の今PRで実装した安全な範囲（リリース未承認）
- `packing-checklist-v50.js/.css`＋`stability.js`：保育園/外出の持ち物ごとに**ストック登録の状態と買い物へのショートカット**を表示。該当ストックの実商品名・単位・カテゴリーを引き継ぐ。
- おむつ/おしりふきに複数サイズ・ブランドがある場合は**本人が商品を選ぶ**。ストック未登録は「不足確定」扱いせず、汎用メモ追加時には確認。買い物に既にある商品は**二重追加しない**。
- チェックは**端末内にのみ保存**され、在庫数量を減らさない。既存の在庫/買い物保存・家族同期の権限処理を変えない。レシートOCR・価格表示・課金は一切変更なし。
- iPhone幅320/393/430のChromium/WebKit E2Eで商品選択・購入反映・数量非変更・リロード保持・同じ候補の重複防止を受入基準に追加。**実機比較・有料意思の実測ではない**。

## 4. 無料とプレミアムの暫定境界

**無料で残すべき核**：在庫と買い物リスト、手入力/基本商品登録、保育園と外出の基本チェック、2人の家族共有（安全性が検証・公開された場合）、端末内の下書き/復元保護。ここを壊す課金制限は初回習慣形成を阻害する可能性が高い。

**有料候補（検証を通過するまでは未実装・課金なし）**：子ども別・曜日別セットの柔軟な自動表示、家族の準備担当/次に買う人の見える化、履歴版バックアップと安全な端末変更の復元、無理のない消費予測、追加の家族枠、OCRのサーバー処理。各機能は競合が無料でも提供していないか、ユーザーが月額を払いたいと感じるかを評価してから決める。

## 5. 単価・費用の一次情報と検証前の概算

- 月398円／年3,980円は**ユーザー構想の仮説**。同額で競合優位が証明された訳ではない。年間3,980円は月398円を12回払う4,776円より約16.7%安い。
- [Stripe Payments日本](https://stripe.com/jp/payments)：成功した国内カード決済の基本手数料を**3.6%**と表示。[Stripe Billing](https://stripe.com/jp/billing/pricing)には継続請求**0.7%**の料金表示。**両方適用される単純な試算**では売上額の4.3%が手数料で、月398円の手数料約17円、差引約381円／年3,980円は約171円、差引約3,809円。ただし税、返金、カード種別、オプション、消費税処理・サービス保守費、OCR処理費は含まない。実契約条件により異なる。
- [Supabase Free](https://supabase.com/pricing)：**データベース500MB・Storage1GB・MAU50,000**等の上限。ユーザーが増えてもこの枠を無限に無料で使えるわけではない。写真、画像変換、レシートOCR、バックアップ履歴の成長で費用と安全性を再検討。
- [Apple Web Push公式](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers)：iOS 16.4以降、**ホーム画面に追加されたWebアプリ**でWeb Pushを利用できる。Safariでページを開くだけで確実にプッシュできると表現しない。通知サーバー費用とユーザー同意の設計が必要。

※プラン/課金の法的条件、Stripeの審査、請求・解約のUI、ストア手数料との関係、データ保護規約は**正式決済実装前に**法令・契約の原典を再検証する。

## 6. 「利益に繋がる」を確認するための計測設計

**現時点ではユーザーデータを自動送信しない。既存のGA4無効／固定費0円方針を尊重。** 計測は合成E2E/任意の本人評価から開始し、実利用者の分析は同意・匿名化・プライバシー告知の別設計が必要。

- **操作性**：3つのシナリオ（朝の保育園、夜の補充、夫婦の買い物）ごとにタップ数・所要秒数・誤操作・やり直し・二重買いを記録。競合の同等タスクとの比較ができるまで「他社より速い」と言わない。
- **習慣化**：7日/30日後に「本当に使った日数」「買い忘れの有無」「必要な準備を代替できたか」を任意のユーザー評価で確認。UIを派手にするより**保存・中断復帰の信頼性**を優先。
- **支払意思**：「無料で使う」「月300円」「月398円」「月480円」の提示順を無作為化した任意ヒアリング、実際に使った機能と支払い意思を分けて取得。架空の販売成績/導入件数を作らない。
- **採用停止線**：実iPhoneで主要シナリオが完了しない、家族間の誤登録/同期破綻が発生、1家族あたり変動費で粗利が出ない、同等シナリオで競合に優位がない、いずれかの場合は売り込みを止めて品質・導線を改修。

## 7. 安全な実装順（既存Draftに集約）

1. **今PR**：S1のローカル準備→買い物連動、汎用名の誤買い防止、ブラウザ回帰、スクリーンショット監査。実世帯・写真・認証情報は利用しない。
2. **公開ゲートを閉じる**：[Issue #96](https://github.com/rodaisuki1023-alt/ig-public-assets/issues/96)の合成2端末のリアルSupabase動的拒否、iPhone Safari実機・PWA受入、セキュリティAdvisorの評価、マージ／公開の別承認。
3. **Phase D本格調査**：実際の買い忘れ・保育園チェック継続・競合操作比較、自由/有料境界の支払い意思、運用コスト試算を検証。
4. **有料実装**：ユーザーが検証データに基づき明示承認した機能から。サーバーOCR・人数枠・決済・新しいDB権限は別承認を要し、**支払い/有料プランは今は存在しない**。

調査は[Issue #103](https://github.com/rodaisuki1023-alt/ig-public-assets/issues/103)と既存「あとこれ 毎日改善チェック」で、新しい競合/機能/料金・ユーザーレビューの変化を追跡し、既存の結論を事実に合わせて更新する。

**新しい仮説**：一番の価値は機能名ではなく「同じ子どものおむつサイズを毎回入力し直さず、誤購入を防ぎ、未完了の準備から買い物へ戻れること」。仕様ごとのエラー防止と再訪の少なさを実測する。この仮説も競合に優位と判定できる証拠はまだない。

### 今回追加した無償の安全な最小実装（統合Draft PR #106）

- 持ち物チェックで複数の在庫商品がある場合、**本人が選んだ商品ID・品名・単位の3点**を同じ端末のチェックリストへ保存する。次回の準備では3点が現存ストックに一致した場合にのみ表示・再選択する。
- **同じIDが別サイズへ使い回された場合、古い選択を自動復元しない**。未確定状態に戻し、本人が改めて選ぶ。選択しただけでは買い物登録も在庫減算も準備完了も行わない。
- チェックリスト旧バージョン1の保存データはそのまま読み取れる。新しい項目は**任意のローカルメタデータ**で、Supabaseスキーマ・家族共有・実世帯情報は変更しない。
- 非同期の「汎用名おむつをメモ追加」の確認中に別タブで準備リストが変更された場合、**古い意思決定に基づく追加を拒否**する。
- 有料と誤認しないよう「機能プレビュー（無料・課金なし）」を明記し、現在の簡易「消費予測」表示は **補充の目安（試算）** と訂正。契約・請求は行わない。
- 後方互換・不正ローカルメタデータ・サイズID再利用・保存後リロード・確認中の別タブ更新・プレミアム非請求表示を回帰テストに追加。**CIは書き込み後の最新HEADで別途判定する**。

### 粗利の損益感度（仮定と公式事実を区別）

参照：[Stripe Payments 3.6%](https://stripe.com/jp/payments)、[Stripe Billing 0.7%](https://stripe.com/jp/billing/pricing)、[Supabase Free条件](https://supabase.com/pricing)、[Apple Developer年間99 USD](https://developer.apple.com/jp/programs/enroll)、[PWA導入](https://web.dev/learn/pwa/installation)。

- **仮定**：国内カード3.6%と継続請求0.7%の両方が常に適用される単純計算、固定手数料/消費税/返金/サポート/サーバー保守は含まず。実契約・取引区分・税務を確認するまで収益予測に使いすぎない。
- 月398円 → 手数料を仮に4.3%（約17.1円）引いて、**約380.9円／有料世帯・月**。年3,980円 → 約3,808.9円／世帯・年＝月換算 **317.4円**（年払いの実際のキャッシュフローは年一括）。
- **サーバーOCR30枚／世帯・月**を仮定するなら、OCR原価が1枚2円/5円/10円の場合、月額契約の残りは約321円/231円/81円／世帯（他の全費用控除前）。OCR単価は**実見積りではなく感度分析用の仮置き**。
- 有料100世帯が月額だけを選んだと仮定した場合、上記手数料後は約38,089円／月（OCR・サーバー・税・サポート前）。売上実績も加入予測も意味しない。
- **追加固定費0円**が条件の間は、サーバーOCR30枚や自動バックアップ履歴を販売約束しない。特に画像保存量・リクエスト数・復元権限はSupabase Free上限を超えうる。ネイティブApp Store公開も年会費を伴うので今の初期0円案に含めない。
- iOSホーム画面PWAはSafariタブと**ストレージが分離される場合がある**ため、実機バックアップ/共有が検証されるまでは機種変更の自動復元を宣伝しない。

### 収益化候補の選抜（優先1〜3位／保留）
