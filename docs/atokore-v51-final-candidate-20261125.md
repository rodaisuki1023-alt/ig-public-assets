## 1. 家族の同時購入：補充予測の取りこぼし（P1）

**原因**
見積もり（`item.track`）は、項目ごとに「後から書いた方が勝つ」形で同期されます。そのため、2人が同時に購入すると、片方の購入分が上書きされて消えていました。

**直し方**
- 購入1回ごとに、商品の別項目 `tp<hash>` として記録します。同期は項目単位なので、別々の購入は両方とも残ります。
- 同じ購入をもう一度送っても、同じ項目に同じ値を書くだけなので、増えません。
- 家族共有中は、共有している買い物行のIDをキーにします。2台で同じ行を「買った」にした場合は、サーバー側の補充（1回）と同じく、1回の購入として扱います。
- 取り消すと、その購入の項目だけを消します。
- 手動の補正は「その時点で見えていた購入」を記録します。補正より前の購入で、補正の時点ではまだ届いていなかったものは、推測で足したり捨てたりせず、「確認」を出します。
- 単位が分からないとき、単位やサイズが変わったときも、足さずに「確認」を出します。
- 古い端末で作った見積もり（観測時刻や「見えていた購入」の記録がないもの）は、その基準日の始まりを観測時刻とみなして、そのまま読みます。
- 30日より前の購入は履歴として扱い、補正したときに片付けます。

**実測（合格の条件をすべて満たしました）**

| 確認したこと | 結果 | 方法 |
|---|---|---|
| 購入前120枚、A・Bがそれぞれ60枚をオフラインで同時に購入し、その後に同期 | **両方の端末で240枚** | 実際の画面、家族2台、エミュレーター（実際のマイグレーションをPGliteで実行） |
| 同期の順序を逆にする／何度も同期する | 240枚のまま | 同上、ユニットテスト |
| Aの購入だけを取り消す | **両方の端末で180枚**（Bの分は残る） | 同上 |
| 2台で同じ買い物行を「買った」にする | 補充も見積もりも1回分 | 同上 |
| 2つの接続から同時に送信（実際のPostgreSQL 16） | 240／再送しても240／遅れて届いた古い書き込みは拒否（stale）／片方を取り消すと180 | `tests/household/purchase-merge-postgres.cjs`（CIにも追加） |
| 補正が、もう一方の購入を見ないまま行われた | どちらの端末も「確認」と表示し、勝手に足したり捨てたりしない | 家族2台のE2E |
| 保存に失敗した | 在庫数は買った後のまま。見積もりは変えず、利用者に伝える | E2E |
| 単位が不明／単位変更／サイズ変更／古い形式の見積もり | 足さずに「確認」を表示／古い形式も読める | ユニットテスト |
