## Supabaseマイグレーション（未適用・承認待ち）

対象は試用版専用プロジェクト `atokore-family-trial`（`vzyxurodowpjltwbgbyc`）。接続とマイグレーション履歴・現行関数を読み取り専用で確認し、対象が未適用であることを確認した。管理画面の手動操作なしで、Supabaseコネクターから適用できる。

- 対象SQL：[20261025090000_atokore_history_w2.sql](https://github.com/rodaisuki1023-alt/ig-public-assets/blob/e56edbca2456d30a8b8cc1c772517cac62a8d3fa/supabase/migrations/20261025090000_atokore_history_w2.sql)。
- SHA-256：`86f28ca53fceb69af0109fb7d21add71903cfda2786e2938b58d2d113c599589`。
- 変更は `public.hh_changes(integer)` の差し替えと実行権限の明示。商品行・数量・世帯・写真を書き換えるSQLは含まれない。
- 新しい返り値に商品ID `record_id` を追加。実行者名は操作時点以前に参加したメンバーを参照し、特定できなければnullを返す。権限は引き続き認証ユーザーのみで、ログイン・世帯所属の検査を維持する。
- 現行関数も `who` を返すため、未適用なら必ず「実行者不明」になるわけではない。ただし新しい実行者判定と商品IDの紐付けは未適用。共有履歴の商品遷移・実行者表示を実Supabaseで完了と扱わない。

通常の推奨順は、ローカル検証 → 承認 → DB適用・確認 → Web公開。旧画面が読む既存フィールドを保つため、今回のようにWebを先に公開した後でも承認後に適用できる。今回はユーザーの「オーナーの承認が取れてから適用」に従い、DBは変更せずWebの公開だけを進める。

承認後の実施手順：

1. 対象プロジェクトと未適用状態を再確認し、現行関数定義・権限を控える。
2. 上記ハッシュのSQL1本をSupabaseの `apply_migration` で `atokore_history_w2` として適用し、適用履歴を記録する。管理画面へ直接貼り付ける方式は使わない。
3. マイグレーション履歴、関数定義、実行権限を読み取り確認する。未認証・非メンバーの拒否と、隔離したテスト世帯で実行者名・商品ID・過去の記録の扱いを確認する。
4. 問題があれば公開前に控えた関数定義へ戻すSQLを新たなロールバックマイグレーションとして適用する。データ削除や履歴の削除は行わない。
