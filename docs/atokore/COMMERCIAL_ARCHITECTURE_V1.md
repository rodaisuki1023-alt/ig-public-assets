# あとこれ：ベビー用品マスター・商用化アーキテクチャ v1

更新：2026-10-18 / ステータス：提案・未本番適用

## 0. 判断とスコープ
- 新規登録は「メーカー → シリーズ → タイプ（パンツ/テープ、缶/キューブ/スティック/液体） → サイズ/段階 → 内容量」の順を基本とする。保管場所・最低在庫数・通知は家族ごとの設定。
- ベビー用品から検証するが、将来の日用品・食品への拡張性を保つ。ブランドを列挙固定せず、ユーザーによる自由入力と別名辞書を併用する。
- アプリを販売してよいという結論は出していない。独自の在庫管理Premiumと、楽天の公開商品紹介媒体は設計・データ・権限・収益を分ける。
- 既存PWAのソース（atokore-live-v125）と保存キー（atokoreTrialV4）は変更せず、本PRは仕様・純粋関数・テストのみ。API・通知・決済・広告は有効化しない。

## 1. 既存コード監査（main: 20049405d3bc214bc7bb1dbd3280bef55bab16f5）
- atokore-live-v125/index.html は items / buys / routines を localStorage.atokoreTrialV4 に保存。例の「オムツ」はブランド・種類・サイズを持たない。
- receipt.js の入庫は商品名と単位を主に使って同一在庫を判定する。『パンパース M パンツ』と『グーン M パンツ』、同ブランドでも別サイズ等の誤統合を防ぐSKU基準が必要。
- atokore-live-v125/index.html、service-worker.js が family.js を参照するが、同ディレクトリにファイルは存在しない。家族共有の配布前に起動経路を統一する。
- v12 の家族共有実装は端末間P2P方式。常時同期・オフライン復旧・同時編集競合を商用版の仕様とみなさない。

## 2. 4つの分離境界（データ構造だけでなく運用でも分離）

### A. アプリ独自の商品定義（first-party）
- `catalog_product`：category（diaper/milk、将来daily）、brand_display、series_display、form、size_code、stage_label、display_name、aliases、created_by、provenance=user_entered|original_editorial。表示名や商標は商品識別目的の文字列で保持。
- `catalog_package`：product_id、pack_quantity、pack_unit（枚/g/mL/本/個）、bundle_pack_count、package_identifier（任意のJAN等。出所明示）、is_active。SKUは固定の包装単位を区別し、内容量の違いを隠さない。
- `catalog_product`の主キーはランダムID。自然キーは正規化済みの category + brand + series + form + size + stage に基づく補助キー。包装差は別のpackage_key。
- 禁止：Rakuten APIで取得した名称・画像URL・価格・ポイント・ランキング・URLをこのテーブルへコピーして永続保存すること。店舗固有の説明文をスクレイピングして転用しない。
- `product_photo`：source=user_upload|licensed_asset|first_party_icon。ユーザー写真は本人の在庫管理に限った権限を設定。権利の不明な画像を共通カタログに昇格しない。

### B. 家族の在庫・買い物・購買履歴（private）
- `household` + `membership`：本人の認証、世帯参加は招待方式。全ての家族データは household_id によるアクセス制御。生の『家族コードだけで全件読める』実装は避ける。
- `stock_lot`：household_id、package_id、location、unopened_packages、open_package_remaining_units（任意）、min_packages、expiration_date（任意）。同ブランド別サイズや同じ包装でも別期限のロットは別管理。
- `shopping_item`：household_id、package_id、requested_packages、status、priority、created_by。サイズ・タイプを明示し、商品変換は利用者の明示操作のみ。
- `consumption_event`：stock_lot_id、差分、日時、操作端末、idempotency_key。利用者による消費速度の計算に使う。競合編集を全体データ上書きで解決しない。
- `purchase_record`：利用者が実際に払った価格・店名・購入日時・総額・領収書（任意）。API取得した販売価格とは完全分離し、利用者の入力・自分のレシートOCR由来として出所を保持。
- プライバシー：写真/OCR画像と会員データは非公開。広告クリック測定に世帯ID、子どもの年齢、在庫の残数、個人の購入履歴などを流さない。

### C. 公開型の商品紹介媒体（public affiliate publishing）
- ログイン無しで誰でも見られる独立したパブリックページ。媒体登録、PR表記、リンク素材の規約順守を公開の前提とする。
- `public_offer` は first-party の公開記事ID・引用元・確認日時・掲載条件と、広告側の短命なレンダリング情報に限定。家族IDと結合させない。
- 楽天APIを使う場合は有料在庫管理システムからAPIアクセスしない。別サービス・別ホスト・別ジョブ・別ストア・別権限で管理したとしても自動的に規約適合するわけではない。公開媒体単独で規約審査する。
- 楽天API取得の価格/販売可能情報は原則24h、その他情報は原則3か月のキャッシュ。期限に達したデータは破棄。API履歴から長期的な価格推移DBを作らない。
- API画像をアプリの商品マスターの汎用写真へ流用しない。広告コードHTMLやリンクURLを独自加工・短縮しない。公表できないクーポン情報は掲載しない。

### D. 通知・課金（affiliate-independent）
- 在庫不足通知の条件は家族の自前データだけで算出。広告・楽天URL・クーポン・商品価格を通知本文に含めない。
- 値下げ通知、プッシュの広告誘導、会員限定画面の広告掲載は未承認のため機能フラグ初期値OFF。適法・規約適合と確認されるまで運用しない。
- Premium候補：高度な履歴/消費予測、任意エクスポート、複数保管場所分析（自前データのみ）。無料の基盤機能と楽天APIの情報をPremiumの対価に含めない。
- レシートOCRはユーザーの入力補助であって、楽天APIに接続しない。新たな外部OCRサービスの利用時は個人情報と従量料金を別途検証。

## 3. 商品の識別・数量ルール
1. おむつ：brand + series + pants/tape + size で商品variantを区別。包材の枚数、セット入りパック数はpackage別。シリーズ変更やサイズ変更は自動統合しない。
2. 粉ミルク：brand + series + form(can/refill/cube/stick/liquid) + stage を別variant。容量 g と mL は互換換算禁止。1箱あたりの本数/スティック数、個包装ごとの容量は個別に保持。
3. 価格比較は可能な場合のみ：商品形態・入り数・出荷条件・税込/税別・送料を整合させて『枚あたり』『100gあたり』を算出。ケース分母不明・サイズ不一致・価格条件不明なら比較不可。
4. 内容量やシリーズの不確かなOCR結果は候補表示に留め、必ずユーザー承認で確定。サイズを推測しない。
5. 同梱セット・数量限定版・テープ/パンツ混在セットは通常の1種類商品へ自動合算しない。
6. 在庫管理単位は『パック』と『残枚数』を分ける。1パックの枚数が違うときに `2パック` を `120枚` と決めつけない。

## 4. ユーザーフロー
商品追加：カテゴリ選択 → ブランド選択/自由入力 → シリーズ → タイプ → サイズ → パック枚数/容量 → 保有数 → 補充目安 → 確認。商品情報の初期候補はアプリ独自入力のみ。
日常操作：一覧では『パンパース/パンツ/M/60枚/2パック』のように区別、ワンタップ±、押し間違い戻し。買い物へ追加する際に選択したpackage_idを維持。
レシート：OCR → 『メーカー/シリーズ/サイズ/枚数』の候補表示 → ユーザーが既存variant選択または新規登録 → 同一包装だけ在庫へ入庫。
買い物：不足候補は自前データで作成。購入先比較を見る場合、将来、適合確認済みの公開媒体を利用者が能動的に開く。

## 5. 最低限の受入条件
- 同ブランドでもテープ/パンツ・S/M・内容量が異なれば勝手に統合されない。
- 同包装だけ同一在庫に安全に加算できる。ユーザーが『変種を切替』しても旧在庫を消さない。
- OCR誤認/在庫0/マイナス入力/ネット断でもデータ破損しない。重複リクエストで二重加算しない。
- 同時に二端末で更新した場合、最後の端末の全件上書きで片方の変更が消えない。
- 商品画像が不明ならアイコン。権利不明画像を自動公開しない。
- 有料契約を解除しても家族在庫情報を閲覧/エクスポートできる退避手段を設ける。
- 楽天APIキーをブラウザへ公開しない。広告URLはアプリプライベートDBに保存しない。

## 6. 変更禁止・明示的レビュー必須
- mainの直接変更、本番反映、広告の発行、課金開始、APIキー取得、プッシュ送信、ユーザー情報収集はこの仕様書だけでは許可されない。
- 規約解釈は法的な保証ではない。各ASP・楽天API・プッシュ運用ごとに別途最新規約を確認する。
