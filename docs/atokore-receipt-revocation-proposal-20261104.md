# レシート確定と家族の除外の同時実行：隔離検証と修正候補

確認日：2026-11-04 JST。公開元は `efc11f747e1a7fdafa927350361c3a029738f552`。
この変更は検証用スクリプト・使い捨てPostgreSQLのCI・資料のみです。アプリ・実DB・公開設定は変更しません。

## 確認する問題

既存の在庫更新等は `atokore_private.lock_member` で世帯のロック取得後にも所属を確認します。
レシートの2関数は `my_household` による開始時の所属確認だけで、同じロックを使いません。
そのため、既に実行中の確定処理がレシート行のロックを待っている間に除外が完了すると、待機終了後に所属を確認せず記録を確定できる可能性があります。

これは在庫保存のRPCとは別の問題です。実世帯での事故、在庫の不正加算、除外後に開始した新規リクエストの許可を確認した、という意味ではありません。

## 再現と候補の比較

`scripts/receipt-audit/revocation.cjs` は接続先をlocalhostの `atokore_ci` に限定します。既存のSQLを使い、架空の世帯・利用者だけを作ります。

1. テスト用のレシート行を別接続でロックします。
2. メンバーの確定処理が実際にロック待ちに入ったことを `pg_blocking_pids` で確認します。
3. 所有者による除外処理を別接続から開始し、確定との前後関係を測ります。
4. 現行SQLでは、除外コミット後に確定が成功するかを確認します。
5. 隔離DB内だけで候補を反映し、同じ入力で除外と確定が直列化されるかを確認します。
6. いずれも、除外完了後の新規呼び出しが拒否されることを確認します。

CIが上記の条件を全て検証して成功した場合だけ、再現・候補の効果を確認済みとして扱います。実行結果はこのPRのCIログと本文を参照してください。

修正候補は2つの関数内の次の宣言を変更するものです。

```diff
- v_hh uuid := atokore_private.my_household(v_user);
+ v_hh uuid := atokore_private.lock_member(v_user);
```

検証は関数の本体だけを隔離DBで置き換えます。既に適用済みのSQLファイルを編集・再適用する手順ではありません。
採用時には追加の差分マイグレーションが必要で、今回の作業には含めません。
