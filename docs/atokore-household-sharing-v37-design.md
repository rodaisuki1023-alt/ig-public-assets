# あとこれ 家族共有（v37）設計

## 1. 現状と判断
- **PR #17（通常版の家族共有）**：PeerJS の端末間（P2P）通信で、「端末時刻が新しい方の在庫全体」を丸ごと送ります。PR #17 では退避・保留・一時停止などの安全策を足しましたが、方式に次の限界があります。
  - 2台が同時にオンラインでないと同期しない
  - 同時に減らした・増やした操作が片方消える
  - 認証は8文字の家族コードだけで、世帯ごとのアクセス制御がない
  - 変更履歴がなく、機種変更後に戻れない
  - 公開の仲介サーバー（PeerJS）に依存する
- **試用版**：家族同期は無効です（ビルド時に`family.js`を空にしている）。
- **判断**：PR #17の方式は使い続けず、作り直します。PR #17から引き継ぐのは考え方だけです。
  - 置き換える前に退避する
  - 「この端末の内容で全員を上書き」には確認が必要
  - 保存したかを読み戻して確かめる
  - 同期の停止状態を表示する

## 2. 方式：端末ごとの操作記録 ＋ サーバーでの1回限りの適用
- **端末側**：在庫・買い物・いつものリストの保存が成功するたびに、前回との差分を「操作」に変えて、端末内の送信待ちに保存します。
  - 数量の変化は「＋2」「−1」のような増減として記録します。
  - 名前などの項目の変更は「この項目をこの値に」として記録します。
  - 商品の作成・削除も操作として記録します。
  - アプリ内の多くの保存経路をすべて書き換えないよう、保存済みデータの差分から操作を作ります。
- **サーバー側**：Postgres の関数1つで、操作の一括適用を1つのトランザクションとして行います。
  - 各操作に端末で作るID（`op_id`、UUID）を付け、サーバーではこのIDを重複不可にします。再送・連打・応答が届かなかった後の再試行でも、二重に加算されません。
  - 数量は増減を足し合わせるので、同時に減らした・増やした操作がどちらも反映されます。0未満にはなりません。
  - 項目の変更は、項目ごとに後から行った方を採用します（端末時刻とop_idで比較。端末時刻は±の範囲を制限）。
  - 削除は「削除済み」の印として残します。後から届いた編集・増減では復活させません。
  - 「買い物完了 → 在庫補充」は1つの操作として扱います。買い物の行がすでに完了していれば、在庫の補充はしません。2人が同時に完了しても二重に補充されません。
  - 世帯ごとに処理を1件ずつ順番に行い、変更番号（seq）の順序が狂わないようにします。
- **受信**：端末は、前回受け取った番号より後に変わった商品の最新状態を受け取ります。そのうえで、まだ送れていない自分の操作を上に重ねて表示します。
  - アプリを閉じていた端末も、次に開いたときに追いつきます。
- **オフライン**：送信待ちは端末内（試用版専用の保存キー）に保存し、再読み込み後も残ります。復帰後に順番に送ります。
- **状態表示**：「端末に保存済み」と「家族と共有済み」を区別して出します（共有済み／送信待ち N件／送信失敗・再試行中／オフライン）。
- **変更履歴**：サーバーに残る操作記録から、誰がいつ何をしたかを表示します（直近50件）。

## 3. バックエンドの選定：Supabase（無料プランで開始）
| 観点 | Supabase | Firebase（Spark） |
|---|---|---|
| 競合・消失対策 | Postgresの関数で、一括適用と重複除外を1つのトランザクションで行える | トランザクションとセキュリティルールを組み合わせる必要があり、重複除外を確実にするのが複雑 |
| 世帯ごとのアクセス制御 | 行単位のアクセス制御＋サーバー側関数で`auth.uid()`の世帯メンバーかを確認 | セキュリティルール |
| 写真 | Storageは無料プランで1GB。非公開バケットに世帯単位のアクセス制御を付けられる | Cloud Storageは従量課金のBlazeプランが必要 |
| 無料枠 | DB 500MB、利用者50,000人/月、転送量5GB。**7日間使われないと一時停止**（手動で再開） | Firestoreは読み取り5万・書き込み2万/日。一時停止はない |
| バックアップ | 無料プランは自動バックアップなし。端末の書き出しとサーバーの操作記録で補う | 書き出し機能は従量課金側 |
| ログイン | メールの6桁コード（PWAでもリンクを開かずに入力できる）。初期のメール送信元は2通/時のため、限定テストの前に外部のメール送信（無料枠）を設定する | メールのリンク、Google |
| スマホでの管理 | ブラウザのダッシュボードで、SQLの貼り付けとキーの確認ができる | ブラウザのコンソール |
| 将来のサブスク | Stripeの通知を受ける関数（Edge Function）で世帯の契約状態を更新。端末からは書き換えられない | Cloud Functions（Blazeプランが必要） |

- **費用が発生する条件**：DB 500MB・転送量5GB/月などを超えた場合、または一時停止を避けたい場合（Proプランは月25ドル）。家族の試用規模では無料枠に収まる見込みです。
- **試用環境の分離**：試用版専用のプロジェクトを使い、通常版や既存データには接続しません。
- **ブラウザに置く情報**：公開キー（anon）だけです。サービスキーなどの秘密情報や管理者権限は置きません。
- **テーブルへの直接アクセス**：すべて拒否し（行単位の制御を有効にしてポリシーなし）、操作はサーバー側の関数だけを通します。

## 4. 世帯・人数・招待
- **2人の数え方**：世帯の人数は「アカウントの数」です（無料は2人、`seat_limit`）。同じ本人の2台目以降の端末は人数に数えません。
- **招待コード**：8文字・24時間で期限切れ・1回限りです。サーバーにはハッシュ値だけを保存し、無効化できます。参加の失敗は1時間に10回までです。
- **参加・脱退・再参加**：参加できる世帯は1人1つです。脱退しても端末の在庫はそのまま残り、同期だけが止まります。
  - 持ち主が脱退すると、最も古いメンバーに持ち主を移します。
  - 最後の1人が脱退した場合も、データは削除しません。
- **機種変更**：同じメールアドレスでログインすると、世帯のデータを受け取れます。

## 5. 個人データから共有への移行
- **世帯を作る人**：最初に、端末の在庫を退避します（端末内のスナップショット、ファイル保存も可能）。そのあと、全商品を共有に送ります。
- **参加する人**：端末に在庫がある場合、無言では置き換えません。次の2つから選びます。
  - 「共有の在庫を使う」：端末の在庫は退避し、「復元前に戻す」で戻せます。
  - 「この端末の商品を共有に追加」：商品ごとに確認します。名前・カテゴリ・単位が完全に一致する商品だけを「同じ商品」として示し、数量を足すかは利用者が選びます（初期値は足さない）。サイズ・容量違いを自動で合算しません。

## 6. 写真
- **v37の限定テスト**：写真は端末内だけに保存し、家族には共有しません（画面にもそう表示します）。
- **共有する場合の設計**（SQLのポリシーは用意済み）：既存の圧縮と位置情報の除去をしたJPEGを、非公開バケット`household-photos/{世帯ID}/{商品ID}.jpg`に保存します。世帯メンバーだけが読み書きできます。無料の1GBでは、約100KB×1万枚が目安です。

## 7. 安全性の要件と、それを確かめるテスト
| 要件 | 確認方法 |
|---|---|
| 同時の増減が消えない | PGliteのSQLテスト＋ブラウザ2つでの操作テスト |
| 再送で二重加算されない | 同じop_idを2回送る、応答が届かず再送する |
| 削除と編集の競合で復活しない | 削除した後に古い編集を送る |
| オフラインの操作が再読み込み後も残る | ブラウザを通信切断した状態で操作し、再読み込みしてから復帰 |
| 別の世帯は読めない・書けない | 別アカウントで、他の世帯への送信・受信・履歴の取得、テーブルへの直接アクセスを試す |
| 招待の期限・無効化・人数上限 | SQLテスト |
| 買い物完了の二重補充 | 2人が同時に完了する |

- **本番相当の確認を自動化できていない部分**：Supabaseの実サービスでのログイン（メールのコード送信）と、実機2台での確認はまだです。手元の検証では、同じSQLをPGliteで動かし、Supabaseの通信の形式だけを真似たエミュレーターを使います。
