# バックアップの重複ID検査（2026-11-10 JST）

## 結論・優先度

**P2：破損・編集されたバックアップ内の同じリストに同一IDの行があると、復元できてしまい、後の削除操作で複数行がまとめて対象になる。** 通常のエクスポートで自然に発生することや、実世帯の被害は未確認。任意の正常ファイルが壊れるという報告ではない。

公開元 `efc11f747e1a7fdafa927350361c3a029738f552` の `parseBackup` は名前・数量・IDの最低限の形式を調べるが、IDの一意性は検査しない。`stability.js` はIDを数値化して行を操作するため、数値7と文字列 `"7"` も同じ行として扱う。合成ファイル（異なる名前、同じIDの在庫2行）を実関数で解析し、受理2行・除外0行、そのIDを実際の `removeByIds` へ渡した後は0行になることを確認した。

PR #94の修正候補 `e7a40a24e784fd115ab19567c4d647ba8c8e6bc3` でも同じ問題が残る。本PRはそのブランチの上に積む。#94の「共有中の復元取り消し」ガードは維持し、既存PR自体を変更しない。

## 修正候補

- ストック・買い物・いつものリストの各トップレベル配列で、既存の不正行の除外後に数値化したIDの重複を検査する。
- 重複があればファイル全体を拒否し、該当するリスト名と復元を中止した旨を表示する。
- 行の削除・合算・採番し直しはしない。IDに結びつく写真や `stockId` の参照を勝手に変更しない。
- 異なるリスト間のID再利用と、別々のセット内の同じ商品参照は許容する。数量やその他の形式判定は今回変更しない。

検査は復元確認の前なので、保存済みデータ・復元前の控え・履歴・写真を変更しない。

## 実行した検証

`tests/atokore-backup-ids.test.cjs`：5件。以下を含む。

1. 各リスト内の重複拒否（数値、数値文字列、先頭0、小数点表記の同値なIDも検査）。
2. 正常な行・写真参照・他リストの同じID・旧形式ファイルの維持。
3. 既存の不正行除外件数の維持。
4. 実物のファイル入力change→解析→復元経路をJSDOMで実行。重複ファイルで確認0回・写真処理0回・描画0回、保存領域とメモリの不変性を検証。
5. 正常なファイルは同じ経路で確認・復元されることを検証。

修正前の #94 headで同じテストを実行すると、重複拒否とDOM経路の保護の2件が失敗、残る3件は成功。修正後は5件すべて成功した。既存の保存起動保護7件も合わせて**12件成功**。構文・差分チェックと試用版ビルドも成功。新テストは既存CIの単体テスト手順へ追加した。

依存は既存CIと同じjsdomを使用する。DOM試験はJSDOMであり、実ブラウザー・Safari・iPhoneのファイル選択試験ではない。GitHub CIの完了はPR作成後に別途確認する。手元のテスト成功をCI成功として扱わない。
