## ① 在庫・操作履歴・送信待ちの原子的な永続保存（`local-journal-v51.js`）

第8回の「localStorageを読み直して3者で統合する方式」は削除しました。

### 原子性の技術的根拠

保存の流れは次の4段階です。

1. **操作への変換**：保存のたびに、そのタブが最後に見た内容との差を「操作」にします。操作ごとに一意のIDを付けます。
   - 種類は、作成・削除・数量の増減（差分）・項目の設定の4つです。
   - 数量は差分で表すので、同時の変更は足し合わさります。
2. **先行書き込みログ（WAL）**：その操作を、同期的にタブ専用のWALへ書きます。
   - 保存先は `localStorage` の `atokoreTrialV4:wal:<タブID>` です。
   - このキーに書くのはそのタブだけなので、書き込みが失われることはありません。
   - WALに書けなければ保存を拒否し、「保存できませんでした」と表示します。成功とは表示しません。
3. **確定（commit）**：**1回のIndexedDB `readwrite` トランザクション**で確定します。
   - 対象のストアは `state`・`applied`・`log` の3つです。
   - トランザクションの中で、確定済みの状態を読み、`applied` にまだないIDの操作だけを適用します。
   - 新しい状態・適用済みID・ログを、同じトランザクションでまとめて書きます。
4. **根拠**：IndexedDBの仕様（IndexedDB 3.0のトランザクションの寿命）によります。
   - スコープが重なる `readwrite` トランザクションは、同じオリジンのすべてのタブにまたがって直列に実行されます。
   - トランザクションは、書き込みをすべて確定するか、まったく確定しないかのどちらかです。
   - したがって、2つのタブの操作が互いを上書きすることはありません。
   - 操作IDとその効果は同じトランザクションで確定するので、各操作は**ちょうど1回**だけ適用されます。

### クラッシュや停止の後

- **確定前にタブが閉じた・クラッシュした場合**：操作はそのタブのWALに残ります。次にどれかのタブが起動したとき、見つけたWALをすべて確定し（IDで冪等）、削除します。
- **確定に失敗した場合（容量不足など）**：操作はWALに残ります。利用者に「確定できなかった」と知らせ、次の操作か再読み込みでやり直します。
- **他のタブへの表示**：確定が完了した後（`oncomplete`）に、`BroadcastChannel` で通知します。受け取ったタブは確定済みの状態を読み直し、その上に自分の未確定の操作を重ねます。逆の順で重ねることはありません。

### サーバーから届いた状態の書き込み（家族共有の同期）

- 同期がサーバーの状態を書くときは「置き換え（replace）」操作にします。この操作には、計算の元にした改訂番号と、反映済みの自分の操作IDを持たせます。
- それ以後に**他のタブ**が確定した操作は、同じトランザクションの中で上に重ね直します。
- そのため、同期によって他のタブの変更が消えることはありません。

### 同期の書き手

- 家族共有の同期を行うのは、Web Locks（`atokore-sync-leader-v51`）を持つ1つのタブだけです。
- ロックはタブの存続中は保持され、タブが閉じたりクラッシュしたりするとブラウザが解放します。その後は、待っていた次のタブがロックを引き継ぎます。
- 同期記録（送信待ち・shadow・map）を書くのは、ロックを持つタブだけです。他のタブは、自分の変更をjournalに確定し、送信はロックを持つタブに任せます。
- Web Locksのないブラウザでは、そのタブは同期しません。

### 旧データ・旧版との関係

- **旧データの取り込み**：最初の起動で、既存の `atokoreTrialV4` を改訂1として確定します（状態がまだないときだけ行うので冪等です）。
- **旧版のタブの書き込み**：旧版の画面が保存キーに直接書いた内容は、要約値（`:jsum`）が一致しないことで見分けます。黙って取り込まず、`atokoreTrialV4OldTabWrite` に退避し、利用者に知らせます。
- **IndexedDBがない環境**：試験用のハーネスなどです。従来どおりの保存になります。

### 試験（両ブラウザ、決定論的な障害注入）

`journal-v51.spec.cjs` と `multitab-v51.spec.cjs` です。Bタブの storage イベントと BroadcastChannel を、アプリの読み込み前から保留する方法で障害を注入しました。

- 別の商品を同時に+1：2/3 になる。再起動の後も同じ。
- 同じ商品を同時に+1：3 になる。
- 確定できないままタブを閉じる：次の起動で1回だけ回復し、二重にならない。
- WALに書けない（容量不足）：保存を拒否し、そのことを表示する。後から適用されることもない。
- 購入 → 古いタブの保存 → 取消：取消は1回だけで、在庫は元どおり。

## ② 補充予測を不変の購入op IDで管理する

- **購入時にop IDを確定**：買い物行のop IDは、購入処理を実行する**前に**決めます（`purchaseOpIdFor`）。
  - エンジンは、そのIDで `complete_buy` を送ります。
  - IDは1回だけ使います。同じ行の買い直しには新しいIDを付けます。
- **予測の記録**：予測の記録には、`o: <op ID>` と `k: 'op:'+op ID` を持たせます。1つの購入に1つの記録です。
- **サーバーでの照合**（`purchase_entry_check_v51`）：記録を有効にするのは、次の4条件をすべて満たすときだけです。
  1. そのop IDが、この世帯にある。
  2. この商品の `complete_buy` である。
  3. `applied`、つまり在庫に加算された。
  4. 取り消されていない。
- **所有関係は書き換えられない**：別のopの記録に書き換えようとする書き込みは拒否します。
- **条件を満たさない記録は隔離**：削除はしませんし、予測にも数えません。対象は次のとおりです。
  - 帰属が不明なもの（`o` がない旧クライアント）
  - 該当するopがまだ届いていないもの：そのop**そのもの**が適用されたときだけ戻します。
  - 不一致のもの
  - 取り消されたもの
- **買い物行による付け替えはしない**：第8回の `sb` による判定は廃止しました。
- **取消時の予測の無効化**：取消（どのRPCでも）と同じトランザクションで、そのopの記録だけを外します（`purchase_forecast_undo_v51`）。
- **Eを切り戻しても予測の保護は残る**：この保護は予測側の仕組みなので、Eの切り戻しでは外れません。切り戻し中に再購入しても、取り消し済みの記録は戻りません。Eを再適用した後も同じです。

試験：`atokore-purchase-op-forecast-v51.test.cjs`

- A購入 → A取消 → 同じ行をBが購入 → Aの記録が遅れて届く：Aは無効のまま。数えるのはBだけで、Bを取り消すと変わるのはBだけ。
- 別のop・別の世帯・帰属不明・同じ行を2台目の端末で購入：どれも数えない。
- 再送：変化しない。
- E切り戻し中の再購入と、その後の再適用：取り消し済みの記録は戻らない。

E2Eの買い直しと、実PostgreSQLでの同時発生（safety5）も確認しました。

## ③ 写真容量の原子的な予約台帳（`photo_storage_reservations_v51`）

- 容量を増やす操作はすべて、まず上限bytesを予約します。対象は、アップロード、移行のコピー、退避、復元です。旧workerも同じ仕組みを使います。
- 予約は、**予算の行1つを `SELECT … FOR UPDATE` でロックした下**で直列化します。

### 閾値の定義

- 計算式：使用量 ＝ 確定済み（未予約分のオブジェクト）＋ 処理中の予約（予約済み・不明・拒否）＋ 今回の上限
- 段階ごとの受付：

| 段階 | 判定に使う値 | 受け付ける範囲 |
|---|---|---|
| 監査 | 使用量 | 70%以上で記録する |
| アップロード・コピー | 予約後の使用量 | 80%未満 |
| 退避 | 予約後の使用量 | 90%未満 |
| 復元 | 予約後の使用量 | 100%以下（90〜100%は復元のための枠） |

- 自動削除はしません。

### 上限bytesの決め方

- コピー元の記録済みサイズを使います。なければバケットの上限、さらになければ退避の記録を使います。
- アップロードは、写真1枚あたりの上限を使います。
- どれも不明なときは、操作しません（`size_unknown`）。

### 予約の扱い

- 予算の行がない、または予約の状態が不明なときは、新しい操作をしません。
- 応答が失われたときやタイムアウトしたときは、`unknown` として数え続けます。解放するのは、ないことを確認できたときだけです。
- 確定するときに実サイズを記録します。予約を超えたものは受け付けません（`rejected` として数え続けます）。
- 同じキーの再送には、同じ予約を返します。

### 試験

- PGlite：
  - 790/1000から：「確定済み＋処理中」で判定する。
  - 不明 → 解放：ないことを確認しない限り解放されない。
  - 予約超過：受け付けない。
  - 復元の枠：80%を超えても復元だけは通る。
  - 上限不明・予算なし：どちらも操作しない。
  - workerの予約：コピーの前に必ず予約し、失敗したコピーは数え続ける。
- 実PostgreSQL（safety6）：
  - 別接続から120 Bを2件同時に予約：両方は通らない。
  - 8件同時の予約：上限を超えない。

### 実運用

- 外部の書き手（ダッシュボードや他の関数）には予算を強制できません。そのため、実運用はHOLDです。

## ④ Eの受付IDの厳密な入力検証

- **処理の前に検証**：`hh_push_v51` は、何かを適用する**前に**入力を検証します。対象は次のとおりです。
  - NULLの配列、NULLの要素、空、型の違い
  - 不正なUUID、重複
  - この呼び出しに含まれないID、他の利用者や世帯のop
  - これらの混在
- **一括拒否**：1つでも不正があれば、呼び出し全体を拒否します（`purchase_receipt_input_invalid`）。購入・在庫・買い物・受付記録・予測は、どれも変わりません。
- **受付を付与する条件**：正の一致（`= ANY … IS TRUE`）のときだけです。三値論理のNULLがすり抜けることはありません。
- **状態の確認**：利用状況の確認は、読み取り専用の `hh_purchase_receipts_status_v51` で行います。
- **再送**：受付の時刻は変わりません。
- **取消の画面**：受付が確定した購入だけを取り消せる表示にします（`undoConfirmed`）。
- **既存の仕様の確認**：次の点は変わっていません。
  - 期限の境界：9:59は取り消せる。10:00・10:01は取り消せない。
  - 599秒の時点でロック待ちになった取消は、600秒を過ぎて拒否される（実PostgreSQL）。
  - 受付のない手動の数量訂正と、その履歴は保たれる。
  - 旧RPC、試用外の世帯は互換性を保つ。
- **保証しないこと**：クライアントの時計や、過去の物理的な購入時刻の真正性は保証しません。

## ⑤ 取消確定後の端末反映

- **調べて分かった原因**：Bの成功後、端末の数量は**次のpull**でしか戻りませんでした。Aの遅延や503によるpullの失敗があると、数量が戻るのが遅れました。
- **修正**：`hh_undo_purchases_v51` の応答に、その取消で変わった行（商品と買い物行、変更番号付き）を含めました。端末は、変更番号が新しいときだけ、それを取り込みます（`adoptRecords`、冪等）。同期全体の状態から成功・失敗を推測することはしません。
- **試験**：
  - Bの購入op IDを指定して、Bの応答の後のpullをすべて503にしました。Aの応答は遅らせ、両方の順で試しました。Bの在庫は**約160ミリ秒**で戻りました。
  - CIでは、WebKitでUTCとJSTの各20回を反復します。
  - 第8回の試験（Bへの503を1回）も、Bのop IDを指定する形に直しました。
- **第9回で原因を特定できなかったChromiumの事象**：応答の順とpullの失敗に依存して、数量が戻るのが遅れたことが原因と考えています。修正後の反復では再現していません。
