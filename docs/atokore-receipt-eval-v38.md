# あとこれ レシート登録 精度評価（v38）

> **使った素材は合成レシートだけです。** 実在の店で受け取ったレシートの画像はありません。利用者の画像も集めていません。
> 実物のレシートでの精度は**未確認**です。以下の数字を、実物のレシートでの精度と読み替えないでください。

## 1. 評価したもの
- 試用版の読み取り方式：スマホ内での文字認識です。tesseract.js 5.1.1（日本語＋英語、psm 6）を使い、有料のAPIは使っていません。
- アプリの処理をそのまま使っています。
  - 画像の前処理（`receipt.js` の prep と同じ値）
  - 行の解析（`receipt.js`）
  - 登録済み商品の候補表示（`receipt-match-v38.js`）
- **2つに分けて測りました**：文字認識（OCR）の精度と、解析・候補表示の精度は別のものです。
  - **A. 文字としてのレシート**：「レシートの文字を貼って読み取る」機能、または文字認識が完璧だった場合に相当します。文字認識は使いません。
  - **B. 画像としてのレシート**：画像から文字を認識し、そのあと解析します。
    - スキャンのようにきれいな画像と、写真のように傾き・ぼけ・低コントラストがある画像の2種類で測りました。
- **自動テスト（Playwright）は、文字を貼る経路を使っています**。結果が毎回同じになるためです。文字認識の精度は確かめていません。モック（固定の入力）での結果を、実際の精度と混同しないでください。

## 2. 素材
- **合成レシート24枚、商品行137行**（`tests/receipt-eval/dataset.cjs`。乱数の種を固定しているので、毎回同じ内容になります）。
  - 店名・住所・日時・電話・レジ番号が入っています。
  - 商品行は、POSでよく見る半角カナの略称です（例：`ﾊﾟﾝﾊﾟｰｽ ｻﾗｻﾗｹｱ ﾃｰﾌﾟM 64ﾏｲ`）。
  - 2個以上の購入行（`2コ X 単1738`）と値引き行があります。
  - 最後に小計・消費税・合計・支払い・点数が続きます。
- 登録済み商品は11件です。紛らわしい組を含めています：
  - おむつのテープMとテープL
  - パンツとテープ
  - 粉ミルクの缶とキューブ
- 商品行の約4割は、在庫にない新しい商品です。
- **未調整の検証用データ（held-out）**：調整が終わった後に書いた商品名20件です（`HELD_OUT`）。この20件を見て処理を直してはいません。

## 3. 結果

### A. 文字としてのレシート（解析・候補表示の精度）

| 指標 | 調整に使った24枚（137行） | 未調整の20件 |
|---|---|---|
| 商品行が出た割合 | 100% | 100% |
| 購入数が正しい（入り数・価格と混同しない） | 100% | — |
| 在庫にある商品で、1番目の候補が正しい | 100% | **69%**（13件中9件） |
| 違う商品が1番目の候補になった | 0件 | **1件**（ほほえみの缶の行で、キューブが1番目に出た） |
| 新しい商品に、在庫の商品を候補として出した | 0件 | 0件 |
| 小計で読み取りを止めた | 24/24 | — |
| 購入日が正しい | 24/24 | — |

- **調整に使ったデータでは100%ですが、その分を割り引いて見てください。**
  - 調整に使ったデータで見つかった2件の失敗（`ﾒｲｼﾞ`＝明治、`ﾀﾏｺﾞ`＝卵）に合わせて、読み方の表を足しました。
  - 現実に近いのは、未調整データの**69%**です。
- 未調整データで候補が出なかった行：
  - `ﾑｰﾆｰﾏﾝ ｴｱﾌｨｯﾄ L`（シリーズ名が違う）
  - `ﾎﾎｴﾐ ｷｭｰﾌﾞ 48ｺ`
  - `ﾘｺ ﾍﾞﾋﾞｰﾜｲﾌﾟ`
- 一度確定した組み合わせは、次回から1番目に出ます。一度確定した後は、ほぼ選び直さずに済みます。これはテストで確認しました。
- **自動で選ばれる商品はありません**。前回確定した組み合わせだけは、最初から選んだ状態になります。違う商品が1番目の候補に出ても、利用者が選ばなければ合算されません。

### B. 画像としてのレシート（文字認識＋解析）

| 指標 | スキャン相当 | 写真相当 |
|---|---|---|
| 商品行が出た割合 | 75.9% | 52.6% |
| 商品名が読める程度に正しい | 21.9% | 21.2% |
| 出た行のうち購入数が正しい | 96.2% | 69.4% |
| 在庫にある商品で、1番目の候補が正しい | 20.3% | 37.5% |
| 違う商品が1番目の候補になった | 0件 | 0件 |
| 余分に出た行（ごみ） | 29行 | 47行 |
| 直す必要がある行（137行中） | 110行 | 115行 |
| 小計で止まった | 23/24 | 14/24 |
| 1枚あたりの時間（中央値／最大）※ | 2.8秒／3.7秒 | 2.2秒／2.8秒 |

※ x86のサーバーでNode.jsを使って測った値です。iPhoneでの時間ではありません。

- **主な原因**：文字認識が、半角カナ（ﾊﾟﾝﾊﾟｰｽ など）を正しく読めないことです。
  - 品名の行は出ても、名前が崩れて候補につながりません。
  - 画像を2400pxに拡大する方法と、白黒にはっきり分ける方法も試しました。どちらも、目立った改善はありませんでした。
- **安全面は保てています**：違う商品が1番目の候補になったことは0件です。崩れた名前には候補を出さないためです。
- **今の文字認識の精度では、写真から読み取っても手入力より手間が減るとは言えません。**
  - 改善の見込みがあるのは、次の2点です。
    - 確定した組み合わせを記憶すること（家族とも共有されます）
    - 文字を貼る経路
  - この結果から、精度の高いサーバーでの読み取りを、有料の候補として準備しています（`docs/atokore-plans-v39.md`）。

### iPhoneに近い条件での時間
- Chromiumの中で、アプリと同じtesseract.js（Web Worker）を動かしました。
  - 1枚あたり2.0〜3.4秒（中央値2.3秒）です。
  - 初回だけ、文字認識の準備に1.2秒かかりました。日本語データの取得を含みます（このサーバーの回線での値です）。
- **CPUを4倍遅くしても、ほぼ同じ時間でした**（中央値2.5秒）。
  - 開発ツールでCPUを遅くする機能は、文字認識を行うWeb Workerには効かないためです。
  - **iPhoneでの時間は、この方法では見積もれません。実機では未計測です。**
- 実機での確かめ方：手順は最終報告の「スマホでの確認手順」に書きます。

## 4. 画面の動きとして確認したこと（自動テスト：Chromium、320px・390px）
- 「64枚入り×1」を64個として登録しません。
  - 例：「食パン 6枚」は1、「2コ X 単1738」は2として扱います。
- テープMの行には、テープMだけを候補に出します。テープLは出しません。
- 値引・小計・税・支払いは、商品にも「読めなかった行」にも入りません。
- 読めなかった行（`MRMI-2`）を一覧に出し、商品として追加できます。
- 購入日（2026-10-20）をレシートから読み取ります。期限日とは別の項目に入れます。
- 保存は確認画面の最後のボタンだけで行い、1回だけです。
  - 合算する商品・新しく登録する商品を表示します。
  - 他の商品は変わりません。
  - 買い物リストから、購入した商品が消えます。
- 同じレシートを再度読み取ると、警告が出ます。
  - 自動では捨てません。
  - 前回確定した商品は、最初から選んだ状態になります。
- 保存に失敗した場合：
  - 在庫は変わらず、組み合わせも記憶しません。
  - もう一度押せば保存できます。

## 5. 限界と次にやること
- **実物のレシートでの評価が必要です**。店ごとに、印字の書体・略称・レイアウトが違います。
  - 許可を得たレシート（例：家族のレシート10〜20枚）を、個人情報を隠したうえで評価用に使わせてもらう形を提案します。
  - 画像はリポジトリに入れません。
- 未調整データで見つかった失敗：
  - 数字と単位の組（`48ｺ`）が商品名の比較を邪魔している
  - シリーズ名の違い
- これを直したら、新しい未調整データを用意して測り直します。同じデータで調整と評価を兼ねないためです。
- 写真の読み取りを改善する方法の候補：
  - 撮影時の補助（傾き・明るさの案内）
  - サーバーでの読み取り（有料プランの候補。費用がかかるため回数で上限を設ける）
