## 2. 実画像での評価

### 2.1 素材と方法

- **素材：オーナーのレシート写真15枚**（依頼文では13枚とありましたが、添付は15枚でした）。
  - 店舗：トライアル4、ヤオコー2、ダイソー2、セブン-イレブン、コストコ、ヤオヒロ、ドラッグストア セキ、カルディ、ウエルシア、生鮮市場TOP
  - 9枚が横向き、1枚が長いレシート（コストコ）です。
- **写真・正解・会員番号などはリポジトリに入れていません。** 評価用ツール（`tests/receipt-eval/real-photos.cjs`）だけを入れ、写真と正解は非公開の場所から読みます。
- **正解は、人が画像を見て書き写したものです。**
  - 内容：商品行の印字名・購入数量、登録済み商品との対応
  - 読めない文字は `?` にして、推測で埋めていません。
  - 登録済み商品は、照合の評価用に作った26件の在庫です（紛らわしい組を含みます。例：おむつのサイズ違い、麦茶2Lと650ml）。
- **調整用9枚と評価用6枚（holdout）に分けました。**
  - 評価用6枚の測定は、改善を終えた後に1回だけ行いました。
  - ただし、正解を作るときに評価用の画像も目で見ています。
- **写真は端末内OCRと同じ処理で読みました。**
  - アプリのコードをそのまま使い、Chromium（ヘッドレス、1スレッド）で実行しました。
  - 外部のOCRサービスには送っていません。
- **画像の解像度：** チャットに添付された画像は1512×2016前後です。iPhoneの元の写真（4032×3024）より粗いため、元の写真での精度は未確認です。

| 指標 | 定義 |

| B. 商品行の検出 | 正解の商品行に対応する行が、確認画面に出た割合 |

| C. 購入数量 | 検出した行のうち、数量が正解と同じ割合（同じ商品の複数行は合計で比較） |
| D. 照合 | 登録済み商品が正解の行で1番目の候補が正しい割合／新しい商品なのに登録済み商品が候補に出た件数／自動で結びつけた件数 |

**評価用6枚の初回測定で見つかった失敗：**

- 650mlの飲料に、登録済みの同じ商品の2Lを1番目の候補として出しました（自動では結びつけていません）。
  - OCRが `650ml` の `l` を `|` と読み、容量の違いを判定できなかったためです。
- `¥99※` の `※` を `X` と読み、2行が価格のない行として「読み取れなかった行」に回りました。
  - 点数の照合（21点に対して19点）でも気づける状態でした。
- 「カスピ海ヨーグルト」に、登録済みの「ヨーグルト」を候補として出しました（自動では結びつけていません）。

**この後、上の2つの原因を店名に依存しない規則で直しました。**

- 補正したもの：`(数字)m|`→`ml`、`¥` の後の `X` を `※` として扱う
- 修正後に保存済みのOCR結果で再計算した値です。**評価用画像を見た後の修正なので、初回測定の値とは分けて読んでください。**
  - 評価用6枚：検出 100%（46/46）、数量 100%、混入 0行、新しい商品への候補表示 1件（カスピ海ヨーグルト）
  - 調整用9枚：変化なし

### 2.4 主な失敗原因（段階別、v48まで）

1. **画像：** 机の木目を文字として読み、商品行の後ろにつないでいました。そのため「価格が行末にある」という前提が崩れ、行が捨てられていました（全レシート）。
2. **画像：** 横向き9枚は、ほぼ何も読めませんでした。
3. **OCR：** 半角カナ（ｸﾞﾘｺ、ﾖﾂﾊﾞﾊﾞﾀｰ、ｺｽﾄｺの品名）を読めませんでした。前処理を直した後も、セブン-イレブンとカルディの品名は崩れていました。
4. **構造：** 次のような表記を扱えていませんでした。
   - `*108`（印が価格の前にある）、`¥238外`、`1.398`（ピリオド区切り）
   - 数量行 `990@ × 4個`、価格のない品名の次に来る `2コX単68`
   - 税の集計行で終わり、小計のないレシート
5. **名前：** 一般名への置換が強すぎて、別の商品を同じ商品にしていました（上の表の4）。

## 3. 誤った在庫を作らないための対策と確認

| 要件 | 対策 | 確認 |
|---|---|---|
| 金額・電話・日付・ポイント・広告を商品にしない | 行の分類（メタ情報）と、小計・合計・税の集計行での停止。合計の大きな文字を読み違えても、税の集計行で止まる | 単体テスト・実画像（混入0行） |
| 値引き・クーポン・税・支払いを商品や数量にしない | マイナス金額、値引・割引・CPN・IRC・まとめ売り。コストコは `CPN` 行と `280-E` の両方で判定 | 単体テスト・実画像 |
| 入り数・容量を購入数量にしない | 購入数量は数量行（4形式）と、会員制倉庫店の数量欄だけ。`11本入`・`1LX15`・`60枚`・`(P×5)`・`3コデ`・`2点 1回` は数量にしない | 単体テスト |
| 数量行の扱い | 数量行は直前の1行にだけ付ける。単価×数量＝金額が合えばそちらを優先（数字の読み違いに強い） | 単体テスト |
| 同じ商品の複数行 | 同じ名前で要確認でない行は合算（例：コストコの同じ品が2行→2点） | 実画像 |
| 小計がないレシート | 合計・税の集計行・支払い行でも止まる | 実画像（ヤオコー2枚） |
| 違う商品を同じ商品にしない | 一般名への置換は7割以上のときだけ。候補でもサイズ・容量・形・ブランドの違いは出さない | 単体テスト・実画像（自動の結びつけ0件） |
| 初めての略称を自動で確定しない | 自動で選ぶのは「前回この印字で確定した商品」だけ（v38から変更なし） | 既存のE2E |
| 読み落としに気づける | 印字の点数と数量の合計を照合して表示。「商品名を読めない行（N点）」「価格も数量も読めない行」を一覧に出す | E2E・実画像 |
| 二重取り込み・連打・保存失敗・通信切断 | 同じ画像・同じ内容なら警告（v38）。最後のボタンの二度押しは1回だけ保存。保存失敗では何も残さない。部品を取得できないときは何も登録せず、次の手段を表示 | E2E（`receipt-photo-v49`、`receipt-v38`） |
| 家族共有中の二重加算・相手の変更の消失 | 保存は既存の確認画面と同期を通る | E2E（`receipt-shared-v49`：A端末でレシート登録、B端末で同じ商品を＋1 → 同期後、両端末で各変更が1回ずつ） |

**気づいた点（今回は変更していません）：**

- 期限を記録している商品（例：消費期限つきの牛乳）は、レシートで「登録済み：牛乳」を選んでも、確認画面では「新しい商品として登録」となり、別の行になります。
- 期限の違うロットを分ける既存の規則（`quick-add.js`）によるもので、二重加算ではありません。
- ただし分かりにくいので、表示を改善するかどうかを判断してほしい点として残します。

## 6. サブスクとしての価値（提案。料金・無料枠は未決定、課金実装は変更なし）

- **サーバーOCRとの比較：**
  - Google Cloud Vision の文字検出は、月1,000枚まで無料、それ以降は1,000枚あたり1.5ドルです（公式の料金ページで確認。下の表を参照）。
  - 月500円・1人月20枚なら費用は小さいです。ただし、写真を外部に送ることになるため、プライバシーの説明と同意が必要です。
  - 端末内OCRで基準に届くなら、送信しないこと自体が売りになります。
- **すぐに課金へ進むより先に：** 限定試用で、1回あたりの修正箇所数（実測）と継続率（2週目にも使うか）を測るのがおすすめです。
