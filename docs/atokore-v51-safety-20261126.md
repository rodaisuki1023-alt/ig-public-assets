## Phase 1　写真の移行中にデータが失われる問題（最優先）

- **Workが再現した内容**
  - 移行後に `upload_sha256` が NULL のままで、一般写真ゲートが `photo_denied` を返していた。
  - 旧写真はすでに削除されていた。
  - 再開しようとすると `photo_not_legacy` になった。
- **修正**（`supabase/proposals/atokore-photo-legacy-migrate-v51.sql` と `photo-orphan-worker-v51.mjs`）
  - commit：
    - 台帳の行に `upload_sha256` とサイズを入れる処理と、商品の参照を切り替える処理を、1つのトランザクションで行います。
    - `upload_sha256` を持たない台帳行への参照の切り替えは、トリガーで拒否します。
  - verified という段階を新しく作りました。
    - ワーカーは、一般写真ゲートと**同じ関数**（`readVerified`）で写真を読み込みます。この関数は、認可・パス・サイズ・SHA-256・JPEGであることを確認し、最後にもう一度認可を確かめます。
    - 読み込んだバイト列が旧写真と同じときだけ `verified` になります。
  - 旧写真の削除は `verified` になってからだけ行います。
    - 削除の直前に、ロックを取って確認し直します（`photo_legacy_delete_ok_v51`）。
    - 別の商品（削除済みのものを含む）が参照している場合や、同じ写真の移行がほかに進行中の場合は削除しません。
    - これを満たすまで、旧写真は残ります。
  - 再開：`begin` は、その商品で途中になっている移行（copying／switched／verified）を、止まった段階から続けます。
  - 復元のリハーサル：
    - `begin` の時点で、商品の写真パスとseqを退避します（`photo_legacy_backup_v51`）。
    - `photo_legacy_restore_v51` を使うと、旧写真が残っている間は商品の参照を旧写真に戻せます。コピーした写真は孤児として回収します。
  - 範囲の制限：
    - 合成世帯の許可リストに入っている世帯だけが対象です（SQLとワーカーの両方で確認）。
    - 扱うバケットは2つの固定バケットだけ、パスは決まった形式のものだけです。
  - 孤児の回収とアップロードの競合：削除の直前に、予約と同じロックの下で台帳を確認し直します。
- **テスト**（PGlite 10件：`atokore-photo-legacy-migrate-v51.test.cjs`）
  - 本物の一般写真ゲートのハンドラーを使い、家族2人がどちらも同じバイト列を取得できることを確認しました。
  - 回帰テスト「写真を取得できない状態では、旧写真を削除しない」：次の3つの場合すべてで、旧写真が残り、状態が `switched` のままであることを確認しました。
    - ハッシュがNULLの場合
    - 写真のバイト列が違う場合
    - 写真の実体がない場合
  - 各段階からの復旧：コピーの失敗、commitの応答の消失、切り替えの後の停止、旧写真の削除の失敗、finishの応答の消失。
  - そのほか：別の商品が参照している写真の保護、復元のリハーサル、商品が変更されたときの移行の中止、孤児回収とアップロードの競合、合成世帯以外の拒否、読み取り確認。
  - 変異テスト：次の修正を外すと、テストが失敗することを確認しました。
    - commitでハッシュを入れる処理
    - 「verifiedになるまで旧写真を消さない」条件

## Phase 2　旧写真バケットの閉鎖条件
- これまでの条件に加えて、次の場合は閉鎖を拒否します。
  - verifiedになったが旧写真を消し終えていない移行が残っている。
  - 台帳にハッシュやサイズがない。
  - **一般写真ゲートと同じ方法で読み取り確認ができていない写真が1枚でもある**（`photo_unread_remain`）。読み取りは、写真の実体を書き込んだ後に、台帳と同じハッシュ・サイズで行っている必要があります。
- 台帳・読み取り確認・移行の各テーブルにもSHAREロックをかけます。そのため、確認の後に状態が変わることはありません。
- 実PostgreSQL（CIの順番で確認）：
  - ほかのテストが残した写真（読み取り確認がないもの、参照も実体もないもの）があると、閉鎖を拒否しました。
  - 同時に書き込まれた旧参照があると、閉鎖を拒否しました。
  - 閉鎖を2つ同時に実行しても、順番に処理されました。
- 旧URLがCDNから消えたかどうかは、実環境で試験するまで**未合格**のままです。

- **原因**

  - 「処理中」の状態とエラーも、購入ごとではなく1つだけでした。
- **修正**（`polish-v44.js`）

  - 「処理中」・エラー・タイマーも、購入1件ごとに分けました。
  - 取消の後の同期は、取消を送った後に始まる同期（`freshSync`）を使います。ほかの取消の同期と重なっても、失敗と判定しません。
- **E2E**（`undo-race-v51.spec.cjs`。サーバーへの応答をネットワークの段階で止めて確認）
  - Aの取消が成功しても失敗しても、Bの取消バー・取消ボタン・Bの10分の期限は残ります。
  - Aの取消を買い物ページのボタンから行い、それが失敗した場合も同じです。
  - 応答の順番が逆になっても、二重にタップしても、正しく動きます。
  - 修正前のコードでは、この4件のうち3件が失敗します。
  - 同時購入の 120→240→180 の回帰テストも合格しています。

## Phase 4　購入取消の期限をサーバー側で守る仕様
最初の草案は、すべての世帯の `hh_undo_purchases` を置き換えていました。また、サーバーが購入を受け取った時刻から10分を数えていたため、40分前の購入でも取り消せてしまいました。

- **採用した仕様**（`atokore-purchase-undo-window-v51.sql`。適用はしていません）
  - 取消用のRPCを別に作りました（`hh_undo_purchases_v51`）。既存のRPCは変更しません。
  - 使えるのは合成世帯だけです。それ以外の世帯には `not_enabled` を返し、アプリは既存のRPCを使います。
  - アプリが新しいRPCを使うのは、設定 `purchaseUndoWindowV51` がtrueのときだけです（既定はfalse）。
  - 期限の起点は、次の2つのうち**早い方**です。
    - サーバーが購入を受け取った時刻（`ops.at`）
    - 端末の購入時刻（`ts`）。ただし、受け取った時刻の30日前から60秒後までの範囲に収めます。
  - 端末の時刻は、期限を**短くする方向にしか**使いません。
    - 時計が進んでいる端末が、期限を延ばすことはできません。
    - オフラインで購入し、40分後に同期した場合は、同期した時点ですでに期限切れです。遅れて同期しても期限は始まり直しません。
  - 9分59秒に取消を始め、サーバーに10分以降に届いた場合は拒否します。このときは何も変えず、アプリは「10分を過ぎたため、取り消せません」と表示します（E2Eで確認）。
  - まとめて送った取消は、1件でも期限切れがあれば全体を拒否し、何も変えません。
  - すでに取り消し済みのものを再送した場合は、期限を過ぎていても従来どおり応答します。
  - 切り戻しは、新しいRPCを削除するだけです。既存のRPC・購入の記録・購入の履歴は、そのまま残ります（テストで確認）。
- **サーバーでの取消が成功した後、見積もりの保存に失敗した場合**
  - 修正内容を残しておき、次の同期のとき、またはアプリに戻ったときにやり直します（E2Eで確認）。
- **ほかの選択肢と影響**（オーナーの判断が必要なときのために）
  1. 端末の時刻を使わず、サーバーが受け取った時刻だけで判定する：仕組みは単純になります。ただし、オフラインの購入は、同期した後にもう一度10分取り消せるようになります。
  2. 期限の直前に始めた取消に、猶予（例：30秒）を設ける：利用者にとっては親切です。ただし、「10:00以降は不可」という条件と食い違います。
  3. 採用した案（早い方の時刻を起点にする）：期限が延びることはありません。端末の時計が実際より遅れていると、期限が短くなる場合があります。その場合は、ストックの数を直接直すよう案内します。

## Phase 5　担当・持ち物共有のSQL
- **ユニットごとの切り戻し**（`supabase/proposals/rollback/`）
  - 担当（C）と持ち物（D）は、それぞれ単独で切り戻せます。
  - 切り戻すときは、そのユニットのデータを退避してから、そのユニットのものだけを削除します。共通の合成世帯許可リストは残します。
  - もう一度適用して restore を実行すると、データが元に戻ります。
  - テストで確認したこと：Cだけを切り戻しても、Dだけを切り戻しても、もう一方は動き続けます。復元した状態のまま、操作を続けられます。
- **家族から抜けた後**
  - 端末に残っていた担当と契約状態のキャッシュを消します（抜けたとき、外されたとき、ログアウトしたとき）。
  - 抜ける前に、担当・依頼・通知・持ち物共有がどうなるかを案内します。
  - サーバー側では、担当の解除と、未送信の通知の破棄を、メンバー表のトリガーで行います。E2Eで確認しました。
- **通知**
  - 送信の直前に、相手がまだ家族にいるか、対象がまだ有効かを確認し直します（`notify_due_v51`）。
  - 「送信済み」の記録は1回だけ付きます（`notify_mark_sent_v51`）。破棄した通知に、送信済みが付くことはありません。
  - **実際の送信はしていません。**
- **古いrevisionで競合したとき**：「家族が先に変更しました。最新の担当を表示しています。」と表示します。合成世帯でない場合（`not_enabled`）と、入力に誤りがある場合（`invalid`）にも、それぞれ案内を表示します。
- **実共有の前に、合成アカウントで受け入れ確認をする手順**（案。実施には別の承認が必要です）
  1. 試用用のプロジェクトに、合成世帯を2つ作り、許可リストに入れる。
  2. iPhone 2台で、次の流れを確認する。
     - 担当の依頼 → 返事 → 家族から抜ける
     - 持ち物の共有 → チェック
     - 購入 → 取消（10分の期限）
  3. 実際の通知は送らず、`notify_due_v51` の結果だけを確認する。
  4. 終わったら、ユニットごとに切り戻してから restore を実行し、手順どおり戻ることを確認する。
