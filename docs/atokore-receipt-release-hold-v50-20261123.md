# あとこれ v50｜レシートOCR正式提供の保留と復活ゲート

決定日：2026-11-23（ユーザーの実iPhone評価に基づく）

## 決定

- **正式公開候補ではレシートOCRの入口を非表示にする**。ホームは「ストック追加」「買い物メモ」の2ボタン。マイページの「レシート一括補充」は通常表示しない。直接 `showPremium('receipt')` を呼んでも通常モードでは開かない。旧デモの `applyReceipt()` も通常モードで在庫を書き換えない。
- OCR解析・過去レシートの処理コード/モデル、ライセンス、保存データを消さない。テストブラウザで **ページ読み込み前** に `window.ATOKORE_RECEIPT_EXPERIMENTAL=true` を設定した場合だけ開発試験で従来のOCR機能を有効化できる。**URLパラメータや一般向けUIから切替はできない**。
- 既存の保有データ・レシート別名・写真・家族データを削除しない。課金・広告・トラッキングも追加しない。
- これはクライアント向けの**公開UIゲート**であり、個人データのアクセス権限を守るサーバー認証の代わりではない。ソースコードの保管を継続するので、技術的にコードを解釈できる人からの解析を防ぐための措置ではない。
- ホーム・買い物・在庫登録・持ち物チェック・バックアップ・写真・家族共有の実装は継続。実Supabase Storageの失効と実iPhone 2台の家族試験は**公開前の独立P1ゲート**。

## なぜ保留するのか

過去のレシート10枚で商品行72/72・数量72/72は検出されたが、商品名の完全一致は57/72（79.2%）。これらは限定サンプルの基礎解析指標であり、**現実の購入商品が正しいストックとして手間なく登録できる品質の証拠ではない**。ユーザーの実機評価では修正負担が大きく製品として不十分だった。

## OCR再開の仮説と実測ゲート

1. **まず無料・端末内で改善**：正規化・スーパー独自の略称と登録商品名の照合、別名辞書（利用者が確定したときだけ記憶）、サイズ/容量/味の比較、購買明細の誤登録抑制、複数商品と日付ロットの判別。保存前の人による一括確認と安全な取消しを維持する。
2. **ベンチマーク**：新規に収集した同意済みの非個人情報レシート（店舗/印字/傾き/縦横/手書き訂正等の偏りを避ける）を別の評価集合として扱う。学習用と評価用を分離して、店舗別・ベビー用品別で結果を報告。私的な家族情報を自動収集しない。
3. **品質指標**：商品名の完全一致率、実際の登録先商品ID一致率、数量の誤加算・二重加算数、合計/税/値引行の誤登録数、店舗別不具合、修正タップ数・所要時間、端末発熱/メモリ落ちを測る。72/72の行検出だけでは合格扱いしない。
4. **試験上の暫定合格目標（未達成）**：商品名・登録先の正確さ95%以上、誤った自動在庫加算0件、中央値の登録完了時間が手入力より短い、iPhone Safariの縦横・複数レシートで失敗理由が分かる。これらはあくまで検証目標であり、誤認識が安全に保留されることを優先。
5. **再公開時の手順**：別Draft PRで精度改善→Chromium/WebKit/iPhone実機→合成家族2端末→独立レビュー→オーナー承認。バグや正答率低下があれば再び非表示。クラウドOCRの導入は費用・データ保護・同意の別審査を通るまで行わない。
